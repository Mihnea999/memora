# Developing Memora

This document describes how to build Memora, test it in a virtual machine and verify changes before
they are merged.

## Building the ISO

The build runs `mkarchiso` inside a privileged Arch Linux container and requires Docker.

```bash
./build.sh
```

The image is written to `out/memora-<version>-<date>-x86_64.iso`.

## Testing in a virtual machine

`test/vm.sh` is a QEMU harness with UEFI firmware, GPU acceleration and audio.

| Command | Purpose |
|---|---|
| `test/vm.sh install` | Unattended installation of the latest ISO into `test/disk.qcow2` (user `memora`, password `memora`) |
| `test/vm.sh run` | Boot the installed disk in a GPU-accelerated window |
| `test/vm.sh live` | Boot the ISO interactively and use the graphical installer |
| `test/vm.sh boot` | Boot the installed disk headless, with VNC on `localhost:5905` |
| `RES=1366x768 test/vm.sh run` | Use a different screen size, for example `2560x1080` or `1080x1920` |

### Development disk

A second disk runs `system/` live from the working tree, so shell and configuration changes can be
tested without rebuilding the ISO:

```bash
VM=dev test/vm.sh install && VM=dev test/vm.sh dev
```

A new development disk needs its helpers connected once, from a terminal inside the virtual machine:

```bash
echo memora | sudo -S mount -t 9p -o trans=virtio,version=9p2000.L share /mnt/share; bash /mnt/share/dev-setup.sh
```

This only modifies the development disk (`~/.config/hypr/user.lua` and `~/.local/bin/memora-dev-boot`),
never the ISO.

### Logs

From login onward, the development virtual machine writes its logs to `test/share/logs/` on the host:

| File | Contents |
|---|---|
| `journal.log` | The complete journal for the boot, system and session, with millisecond timestamps |
| `shell.log` | Shell output: QML errors, warnings and `console.log` |
| `hyprland.log` | Hyprland log |
| `events.log` | Hyprland events (windows, focus, workspaces) with timestamps |
| `dev.log` | Start-up time of the development helpers |
| `prev/` | The same files from the previous boot |

The same login starts a command loop (a script written to `test/share/cmd` runs inside the session and
its output is written to `test/share/cmd.out`) and a `ydotoold` instance on `/tmp/.ydotool_socket` for
pointer automation. Restart the shell with `bash /mnt/share/shell-restart.sh` to keep logging.

This behaviour is defined in `test/share/dev-init.sh`, which is edited on the host and runs at the next
login.

## Change workflow

A change is complete only when it has been exercised on a running desktop and delivered as a new image.

1. **Test in the virtual machine.** Log in, confirm that the shell starts without errors and use the
   change as a user would: keyboard, pointer and the affected application. Static QML checks or
   off-screen loading are not sufficient. Hyprland plugin changes are built inside the virtual machine
   with `system/plugin/build.sh`.
2. **Build a new image** from the branch with `./build.sh`.
3. **Install and verify the image** on a clean disk with `test/vm.sh install` followed by
   `test/vm.sh run`, and confirm once more that the shell starts and the change works.
4. **Merge into `main`** as a fast-forward. Never force-push. If any step fails, fix the issue and
   restart from step 1.

## Asset generation

Icons, logos and wallpapers are generated by the scripts in `tools/`:

| Script | Output |
|---|---|
| `tools/gen-art.sh` | Logos, wallpapers and icons |
| `tools/icons.py` | Memora icon theme |
| `tools/flow.py` | Ember and Tide wallpapers |
| `tools/play.py` | Sorbet, Lagoon, Petal and Bubbles wallpapers |
| `tools/silk.py` | Silk wallpaper |

## Releases

Memora updates are distributed from the address set in `URL=` in `/etc/memora/update.conf` and are
installed only when signed by a key in `system/keys/*.asc`. Signed releases are produced with
`tools/release.sh`.
